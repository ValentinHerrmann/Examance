# CI and dependency audit

**Backend dependencies come only from `backend/uv.lock`** (issue #244). CI and `backend/Dockerfile` export the lock (`uv export --frozen --no-emit-project`) and install it with `--require-hashes --no-build`: exactly the locked versions, hash-checked wheels only, so no dependency runs setup code. The app itself is not installed as a package; it runs from its source directory (`PYTHONPATH`). CI fails when `pyproject.toml` changed without `uv lock` (`uv lock --check`), and `pip-audit` audits the exported lock (dev extras included) without installing anything. Versions move only through a deliberate `uv lock --upgrade` / `--upgrade-package <name>`, which is also the fix for a pip-audit advisory. uv is pinned like everything else: `astral-sh/setup-uv` with `version` in CI, the digest-pinned `ghcr.io/astral-sh/uv` image in the Dockerfile; bump both together, and use that uv version locally so the lock's `revision` stays put. `npm ci` installs the frontend lockfile with `--ignore-scripts`.

**Third-party actions are pinned to a full commit SHA** with the tag as a comment (`uses: docker/login-action@<sha> # v3.7.0`, SonarCloud S7637); GitHub's own `actions/*` keep their major tag. Downloads in Dockerfiles and scripts use `curl --proto '=https' --tlsv1.2` (S6506).

The frontend `npm audit` gate is deliberately scoped to `--omit=dev`: the build toolchain (Vite / SvelteKit / Svelte) never ships to a browser, so a dev-server-only advisory must not block deploys. The full tree is still reported (non-blocking). `@sveltejs/kit` sits in `devDependencies` for that reason, as in the SvelteKit template.

The `--omit=dev` tree is still not only shipped code: `@embedpdf/snippet`'s packages declare non-optional `svelte >=5` / `react` / `vue` peers, so npm counts Svelte (and its `devalue`) as "prod" although only the preact build is bundled.

Their advisories hit the gate. Fix with a lockfile bump (`npm audit fix`), never `--force`.

Two dev-only advisories are handled outside the lockfile bump (issue #248): `frontend/package.json` `overrides` lifts the `minimatch` of `@typescript-eslint/typescript-estree` to 11 (GHSA-g3hv-75wg-m249; no patched 10.x, same API); drop it once typescript-eslint depends on minimatch 11. `deepmerge` (GHSA-gcqx-w48m-w2h4, via `@sveltejs/vite-plugin-svelte`) has no patched release and only merges our own Svelte config, so the alert is dismissed, not overridden.

The `e2e` job runs the Playwright layout and accessibility specs (`frontend/e2e/layout.spec.ts`, `a11y.spec.ts`) on the `desktop`, `ipad-portrait` and `phone` projects (issue #183), so they cannot rot again. It is a matrix with one job per device and check group (`routes`: the route loops of `layout.spec.ts`; `a11y`: `a11y.spec.ts`, desktop and phone only; `shell`: the rest of `layout.spec.ts`), so the eight jobs run side by side in about three minutes; inside a job Playwright keeps one worker, since parallel workers made Argon2 and the dev server flaky. A new spec file runs in CI only once a group's `args` names it; a new test in `layout.spec.ts` lands in `shell` unless it matches the `routes` grep. The job caches `frontend/node_modules` (keyed on the lockfile and Node version, `npm ci` only on a miss) and installs only Chromium's headless shell. The browser's API calls go to the in-memory fake (`frontend/tests/helpers/fakeApi.ts`), so no backend or database runs. It installs with `--ignore-scripts` (the only install script in the tree is macOS-only fsevents) and calls the locked binaries in `node_modules/.bin`, never an on-demand `npx` download (SonarCloud S6505/S8543). It needs `svelte-kit sync` before Playwright loads its config (the tsconfig extends the generated `$app/tsconfig`), and on failure it uploads the HTML report as the `playwright-report-<device>-<group>` artifact. The functional suite and the other device projects stay local for run time; run them with `npm run test:e2e`.

The `docs` job builds the VitePress site in `docs/` (its own `package.json`, separate from the app), installing with `--ignore-scripts`: the only install script in its tree is macOS-only fsevents. VitePress fails on dead internal links; links that leave the site (sources, PDFs, Marp slides) are rewritten to GitHub by `docs/.vitepress/config.mts`. Its dev-server advisories are not audited: the site is static HTML. VitePress is on the 2.x pre-release because 1.6 is stuck on Vite 5, whose dev-server advisories (Vite, esbuild, launch-editor) have no 5.x fix (issue #248); `vitepress-plugin-mermaid` still declares only a VitePress 1 peer, so `overrides` points it at our VitePress (`"$vitepress"`); drop that once the plugin accepts VitePress 2. `vitepress-plugin-mermaid` only accepts mermaid 10 or 11, so `docs/package.json` keeps mermaid 11 and forces the patched katex (GHSA-238p-pmpm-9mq7) through `overrides`; drop the override once the plugin accepts mermaid 12.

## SonarCloud

SonarCloud runs as automatic analysis (no scanner step in the workflows); its settings live in the root `.sonarcloud.properties`. The quality gate allows at most 3 % duplication on new code. The i18n catalogs are excluded from copy-paste detection because `en/*.ts` mirrors `de/*.ts` key for key by design. Loops that await on purpose one step at a time (memory bounds, the single LaTeX worker, the compile rate limit) carry `// NOSONAR: <reason>` on the flagged line instead of being parallelised. Other accepted findings, each with its reason on the line: HMAC-SHA1 in `services/totp.py` (RFC 6238, authenticator apps), the seeded PRNG of the demo scan generators; the demo accounts in `docs/demo-instance/data/` are excluded in `.sonarcloud.properties` (JSON has no comments). Python accepts only `# NOSONAR(<rule>)` (or a bare `# NOSONAR`), so there the reason goes on its own comment line above; `# NOSONAR: …` is malformed and silently ignored (S7632), while JS/TS keep `// NOSONAR: <reason>`. Never NOSONAR a finding that is a real risk; if Sonar ignores a NOSONAR (YAML), mark it Accepted in the SonarCloud UI with the same reason. Build scripts take path arguments only inside `frontend/` (`scripts/cli-path.mjs` `resolveInside`). SonarCloud's S930 flags `Depends(..., scope=...)` as an unknown argument (its FastAPI model predates the parameter); `DbDep` in `backend/app/database.py` carries a NOSONAR for it. A path that reaches a spawned command never comes from the command line at all (S8705). No database password is a literal (S6698, issue #253): CI's throwaway database uses trust auth and has no password, `docker-compose.yml` reads `POSTGRES_PASSWORD` from the root `.env` (template `.env.example`), and the VS Code configs load `backend/.env`; the dev default lives only in those templates.

**Before every push, run `make sonar-check`** (`scripts/sonar-check.sh`). SonarCloud only reports after CI, so this local stand-in runs its most frequent rules on the files changed against `origin/main` (`BASE=<ref>` for another base) and reports only findings on changed lines (`scripts/changed_lines.py`); old findings elsewhere do not drown new ones.
- Backend and `scripts/`: ruff preview rules RUF029 (S7503, `async` without `await`), PT011/PT012 (S5778, one call in `pytest.raises`), PT018 (S9073, composite asserts), FAST002 (S8410, FastAPI dependencies through `Annotated`) and `S` (security).
- Backend `app/`: `flake8-cognitive-complexity` at 15 (S3776).
- Frontend: `eslint-plugin-sonarjs` (`recommended`, with type information so rules such as S2871 work) through `eslint.sonar.config.js`. The normal `npm run lint` and CI do not load it, so the existing code is not suddenly red.

A finding it reports is fixed before the push, or carries a NOSONAR with its reason as below. It mirrors only part of SonarCloud, so the API check after CI stays. In particular it cannot see SonarCloud's taint rules (pythonsecurity/jssecurity, e.g. S8707 path traversal): a script never opens a path taken from its command line; it reads stdin (as `scripts/changed_lines.py` does) or resolves the path inside its tree (`scripts/cli-path.mjs` `resolveInside`).


## README code statistics

The header of `README.md` mixes shields.io badges (GitHub, SonarCloud project key `ValentinHerrmann_Examance`) with two generated charts. `.github/workflows/stats.yml` runs `.github/scripts/code_stats.py` on every push to `main`, counts the tracked files per area (frontend, backend, frontend tests, backend tests, docs; generated files, lockfiles, `openapi.json`, binaries and `frontend/static/{core,example-data}` are skipped) and pushes the results to the orphan `badges` branch. Each area counts its code lines only (blank and comment lines excluded, simple line/block comment detection per file type; Markdown is all prose lines); comment lines of all areas form their own "Comments" series after docs. The README shows `code-history.svg` (stacked areas) and `code-history-lines.svg` (one line per area) side by side, both half the table width so they render at 1:1; `code-stats.svg` (the current table) and `stats.json` are still generated but not shown. All SVGs are light/dark aware. History has one sample per day (the last first-parent commit of that day, read with `git ls-tree`/`git cat-file`, no checkouts), cached in `history.json` on the same branch so a run only recounts new days; bump `HISTORY_VERSION` in the script whenever the series, skip rules or counting change, so the whole history is recounted. Nothing else reads that branch and CI ignores it (`[skip ci]`). To add an area, extend `AREAS`, `ORDER` and `COLORS` in the script.
